# PX4 / ArduPilot 在环仿真扩展设计

当前边界：C++ 只接收实际推力和机体系力矩。本文的飞控通信、传感器调度、执行器映射、限幅、响应与延迟均由 Python/外部适配层承担，不能重新放回物理 `step()`。


调研日期：2026-09-10。**本文是后续架构与验收计划，当前未实现或连接 PX4、ArduPilot、MAVLink 或飞控硬件。**
用户提到的 APM 在本文中按 ArduPilot 软件栈理解；具体板卡、固件版本及协议必须在实际接入时固定，不默认旧 APM 板卡具备所需能力。

## 目标与路线

CSim 继续作为无人机及吊载的物理后端，飞控运行真实的估计器、控制器和控制分配。
先验证软件在环 SITL，再选择具体硬件评估 HITL/Simulation-on-Hardware。
Python 配置实验、任务和日志分析；viewer 读取真值及估计值，协议收发与物理步进不依赖窗口。

| 路线 | 飞控运行位置 | CSim 后续接入方案 | 当前判断 |
| --- | --- | --- | --- |
| PX4 SITL | 主机上的 PX4 进程 | 独立 Simulator MAVLink API 适配器 | 适合第一条完整飞控闭环路线 |
| ArduPilot SITL | 主机上的 ArduPilot 进程 | 独立 JSON physics backend 适配器 | 可并行作为另一协议后端，复用物理与传感器层 |
| PX4 HITL | 支持目标配置的真实飞控板 | 依据固件的 HIL 消息通路和可用串口/网络接入 | SITL 验收后再评估实时性和硬件兼容性 |
| ArduPilot Simulation-on-Hardware | 支持该构建的真实飞控板 | 核实目标板、固件构建和外部 JSON 后端支持 | 不能直接假定等同于 PX4 的 HITL 接法 |

PX4 官方为外部仿真器提供传感器输入、执行器输出的 Simulator MAVLink API；Gazebo 的 `gz_bridge` 和 PX4 内部 SIH 使用其他路径。因此这里选择 MAVLink 适配器作为 CSim 的候选接入方式，未声称所有 PX4 仿真器都使用 MAVLink。[PX4 仿真接口](https://docs.px4.io/main/en/simulation/#simulator-mavlink-api)

ArduPilot 官方提供 UDP JSON 物理后端接口。硬件上的 Simulation-on-Hardware 是另一种部署方式，外部 JSON 后端需要对应板卡和专门构建配置。[JSON 接口](https://ardupilot.org/dev/docs/sitl-with-JSON.html)、[Simulation-on-Hardware](https://ardupilot.org/dev/docs/sim-on-hardware.html)

## 模块边界

以下是拟议结构，尚未创建相应目标或导出 API：

```text
Python 实验 / 地面站 ——任务与指令——> PX4 / ArduPilot
                                         |
                                  电机/舵机输出
                                         v
                           协议适配器 + 通道映射
                                         |
                           执行器响应 / 推力与反扭矩
                                         v
                              CSim 固定步长动力学
                                  |             |
                           真值 -> 传感器模型    真值快照
                                  |             |
                             协议适配器       日志 / viewer
                                  |
                                  +------> 飞控估计器
```

建议新增 `include/csim/sensors/`、`include/csim/actuators/`、`src/integration/px4/`、`src/integration/ardupilot/` 和独立无窗口运行入口 `apps/flight_bridge/`。
这些名称是设计建议，不表示已有实现。MAVLink 等协议依赖仅由可选适配器目标持有，不能进入数学库或动力学头文件。

适配器处理消息编码、连接、序号、单位、坐标、配置和生命周期；传感器层把真值变为测量；执行器层把电机命令变为实际力与力矩。
飞控闭环中的控制分配由飞控负责，CSim 不再额外叠加本地 CTBR/PID 内环。若运行自研控制器实验，应显式选择不同控制源，保证每个执行器只有一个指令来源。
相关规划见 [控制与响应模型](control-and-response-models.md)。

当前 viewer 的 `Scene` 包含一个内嵌演示运行器，使用墙钟预算调用固定步长；它适用于观察算例，不是飞控同步调度器。
接入在环系统前，必须让无窗口运行器独立拥有物理数据和时钟，viewer 通过有界快照队列订阅。
渲染可丢弃过时快照，但不能让渲染阻塞传感器发布、执行器接收或物理推进。
CSV 回放只是显示记录，不可作为飞控闭环的实时传感器输入。

## 两种协议分别实现

### PX4

适配器以 `HIL_SENSOR`、`HIL_GPS` 等消息供给所需传感器，以 `HIL_ACTUATOR_CONTROLS` 接收执行器输出。
`HIL_STATE_QUATERNION` 可供真值对照，不能据此省略估计器所需的传感器路径。
端口、系统/组件 ID、机型、解锁状态和连接角色应配置化；官方当前 MAVLink SITL 示例由仿真器监听 TCP 4560、PX4 主动连接，该通道区别于地面站和 Offboard 链路。[PX4 消息与连接说明](https://docs.px4.io/main/en/simulation/#simulator-mavlink-api)

需要逐条核对所选固件实际使用的消息、时间戳、字段更新掩码和通道含义，并固定 MAVLink dialect/生成代码版本。
归一化执行器输出不能直接当作牛顿值，解锁/停机标志也不能忽略。
字段单位以对应消息定义为准，不以 Python 状态列表的顺序或量纲直接套用。[MAVLink 消息定义](https://mavlink.io/en/messages/common.html#HIL_SENSOR)

### ArduPilot

JSON 后端并非双向 JSON：飞控输出是含 magic、`frame_rate`、`frame_count` 和 PWM 数组的二进制包，后端回送 JSON。
当前官方示例使用 UDP，物理后端监听 9002，并向数据包来源地址回复；支持 16 或 32 个输出通道，需检查对应 magic 和长度。
JSON 包含绝对物理时间 `timestamp`、IMU、NED 位置/速度，以及姿态或四元数。适配器须处理首尾换行和浮点序列化。
重复序号可能是重发，不能重复积分；序号复位需要新的会话/重置策略，不能误判为普通乱序。[ArduPilot JSON 协议原始说明](https://github.com/ArduPilot/ardupilot/blob/master/libraries/SITL/examples/JSON/readme.md)

SITL 的普通 UDP JSON 后端和 Simulation-on-Hardware 的可用通信/构建方式应分别验证，不复用未经核实的启动参数或假设。
实际实现前记录测试的固件提交、目标机型、板卡和启动命令；本文不提供尚未验证的 CSim 启动命令。

## 坐标与传感器语义

CSim 内部保持局部 Z-up 世界系 W 和 FLU 机体系 B。飞控适配边界采用目标协议要求的 NED 导航系 N、FRD 机体系 F；接口字段仍逐项核对。
设 `C_NW` 将 W 分量变为 NED，`D_FB=diag(1,-1,-1)` 将 FLU 变为 FRD，则本项目的转换推导为：

```text
p_N = p_origin_N + C_NW*p_W
v_N = C_NW*v_W
R_NF = C_NW*R_WB*transpose(D_FB)
Omega_F = D_FB*Omega_B
```

四元数应由完整的 `R_NF` 或等价旋转复合得到，不能只对某一个四元数分量取负。
只有显式约定 W 的 X 指北、Y 指西时，`C_NW=diag(1,-1,-1)` 才成立。
CSim 当前的 W 没有地理绑定，因此需要额外配置世界原点经纬高、水平参考航向和高度基准，不能把 W 默认为 ENU，也不能只翻转位置的 Z。

机载 IMU 在质心、无安装偏角时，加速度计的理想测量是比力：

```text
specific_force_B = transpose(R_WB) * (acceleration_W - gravity_W)
specific_force_F = D_FB * specific_force_B
gyro_F = D_FB * angular_velocity_B
```

它不同于当前 `acceleration_W`。静止水平悬停时，FRD 理想加速度计 Z 分量为 `-g`；自由落体时理想比力为零。
必须使用包含吊载反作用力的无人机加速度，而不是吊载加速度。
若 IMU 有机体系位置偏移 `r_B`，传感器点加速度还需加上 `R_WB*(alpha_B×r_B + Omega_B×(Omega_B×r_B))`，再变换到传感器安装坐标。
以上是拟议的物理传感器模型推导；协议适配测试应验证飞控收到的具体分量和单位。

| 传感器 | 第一轮闭环 | 后续扩展 |
| --- | --- | --- |
| IMU | 正确的比力和角速度，独立采样周期 | 噪声、偏置、随机游走、量化、安装偏置与延迟 |
| GPS | 经配置原点转换的位置、NED 速度和时间 | 低更新率、噪声、失锁、延迟、卫星/精度字段 |
| 气压计 | 与高度基准一致的压力和温度 | 漂移、噪声、旋翼压力影响 |
| 磁力计 | 配置当地地磁向量并变换到机体 | 磁偏置、软硬铁误差与干扰 |

各测量保存采样时间和送达时间，真值、加噪测量、飞控估计分别记录。GPS 高度、气压高度和局部 Z 的零点不能混用。
不要让全零磁场、错误重力符号或不一致高度进入估计器后，再用控制器增益掩盖初始化问题。

## 执行器与地面流程是前置条件

当前 `DroneControl` 接受理想总推力与质心力矩，尚不能直接接收飞控的多电机输出。
需先配置旋翼数量、每个旋翼在机体系的位置/推力轴、旋转方向、通道映射和停机值，再建立 PWM/归一化命令到转速或推力的映射。

拟议计算链为：命令限幅 → 已辨识的响应/纯延迟 → 单旋翼推力和反扭矩 → 合力及关于质心的力矩。
如采用 `f_i=k_f*omega_i²`、`tau_i=sign_i*k_m*omega_i²`，系数、转向和量纲必须记录，不能用 viewer 的旋翼圆盘推断实际动力学参数。
饱和、失效、解锁前输出和紧急停机都需有独立测试；若倾转旋翼产生非机体 Z 向合力，还需扩展现有总推力输入模型。

**当前绷紧模型无法完整覆盖地面解锁和起飞过程。** 零推力静止初值要求零张力，而本模型只支持 `T>0`，也没有地面接触。
第一轮应先验证无吊载机体、执行器及传感器，再补地面支撑/起落和绳索松紧事件。
专门设置的空中绷紧初值可用于受限研究，但不能据此声称已支持飞控的常规解锁、起飞和着陆流程。

## 时间、同步与故障

| 模式 | 时间推进 | 显示暂停 | 超时处理 |
| --- | --- | --- | --- |
| 当前本地 viewer 演示 | 固定物理步长，墙钟只分配计算预算 | 可暂停演示 | 允许减慢播放，保留步长 |
| 后续 SITL | 与所选飞控协议协调的 lockstep/调度 | 冻结画面不冻结后端；全系统暂停须显式协调 | 超时停止并记录原因，或按事先声明的策略处理 |
| 后续 HITL | 服从硬件实时约束和所选固件时间机制 | 只能冻结显示 | 记录丢帧、延迟和超期，不能任意缩放硬件时钟 |

PX4 官方介绍了仿真锁步和速度缩放能力，但 CSim 的适配器仍需实现并验证具体握手；当前 viewer 的速度倍率不能当作已经完成了 PX4 lockstep。[PX4 时间同步说明](https://docs.px4.io/main/en/simulation/#run-simulation-faster-than-realtime)

拟议调度器使用明确的物理 tick/仿真时间，不以 `glfwGetTime()` 或渲染帧数生成传感器时间戳。
收到某时刻的执行器指令后，在规定区间保持输入，以固定物理子步积分；在传感器采样时刻生成测量，再按协议交互。
子步与传感器/控制周期不整除时应设计确定性调度，不临时增大 RK4 步长来追赶网络或画面。
多个客户端不能同时步进同一份物理数据；Python 设置实验指令，后端是物理状态的唯一写入者。

连接使用显式地址、端口和机号配置，最初仅在本机回环联调。
处理断连、重连、飞控重启、重复/过期包和数据队列上限；保存最后有效指令的时间与过期状态，不能无期限假装旧指令仍然有效。
开始硬件验证前另行确认板卡、固件和物理输出隔离；本轮开发不刷写飞控或操作真实执行器。

## 分阶段验收

1. 坐标适配：三轴平移、正负姿态旋转、四元数往返；悬停比力与自由落体零比力；传感器偏置点加速度。
2. 执行器与传感器：电机通道、旋向、单电机力矩、饱和、停机；采样率、噪声种子、延迟和单位检查。
3. 协议回环：不运行飞控也能测试编解码、畸形包、截断包、序号、重传、时间戳及超时。
4. 无吊载 SITL：完成估计器初始化、解锁、悬停和基本位置任务，对比真值与估计值。
5. 吊载 SITL：补齐初始/地面/绳索模式后验证摆动、反作用力、风扰动和控制响应；保持已有无阻尼基准。
6. 重现性：记录固件提交与参数、CSim 代码/配置、坐标与地理原点、传感器种子、协议日志；改变 viewer 刷新率或关闭窗口不改变闭环轨迹。
7. HITL：选定具体板卡，验证实时裕量、链路吞吐、延迟分布、断连恢复和输出隔离；未通过前不宣称硬件兼容。
